# Dropdown-Select Tool Fix — Design

**Date:** 2026-07-04
**Status:** Approved

## Problem

The agent fails on native `<select>` dropdowns in two compounding ways:

1. **Advertised-but-unregistered tool.** The system prompt (`src/agent/context/prompt/system.md` lines 71, 93, 97) instructs the agent to use `menu_tool` for `<select>` elements, and `menu_tool` is fully implemented in `src/agent/tools/service.py`. But `BUILTIN_TOOLS` in `src/agent/tools/__init__.py` omits it — the tool is imported and then never registered. The LLM is told the tool exists, calls it, and the call fails as an unknown tool.
2. **Quoting bug in the fallback path.** After the `menu_tool` call fails, the agent falls back to writing its own `script_tool` JavaScript. For option labels containing an apostrophe (e.g., `Mechanic's Lien`) it generates broken single-quoted strings (`'Mechanic's Lien'`), so the fallback fails too.

Additionally, the existing `select_option` implementation (`src/agent/browser/service.py`) fails silently: its injected JS returns `false` when the element is missing and selects nothing when no label matches, but `menu_tool` discards the return value and always reports success. The agent receives false success and never retries.

## Scope

Native `<select>` elements only. Custom dropdowns (React-Select, MUI, headless UI, etc.) continue to be handled via `click_tool` / `script_tool` as today; this design only improves the error message the agent sees when it points `menu_tool` at one.

## Design

### 1. Registration

Add `menu_tool` to `BUILTIN_TOOLS` in `src/agent/tools/__init__.py`. The system prompt already documents the tool correctly; no prompt changes are needed.

### 2. `select_option` returns a structured result

Rewrite the injected JS in `Browser.select_option` (`src/agent/browser/service.py`). Labels continue to be passed via `json.dumps`, keeping quoting safe for apostrophes and any other special characters. The script returns one of:

- `{"error": "not_found"}` — the xpath resolved to no element.
- `{"error": "not_select", "tag": "<tagname>"}` — the element exists but is not a `<select>`.
- `{"selected": [...], "notFound": [...], "available": [...]}` — normal case: which requested labels matched, which did not, and the dropdown's full option list. `available` is truncated to the first 30 option labels to keep tool output small.

Matching rules: requested labels are compared exactly against `option.text.trim()`. No fuzzy matching — instead, the `available` list makes near-misses (curly apostrophe `’` vs `'`, stray whitespace) self-correcting: the agent sees the real option text and retries with it verbatim.

Selection semantics:

- **Single-select:** the first requested label that matches sets `selectedIndex` to that option.
- **Multi-select:** every matching option gets `selected = true`; previously-selected options not in the requested labels are deselected.

After any selection change, dispatch both `input` and `change` events (with `bubbles: true`), since some frameworks listen for `input` rather than `change`.

### 3. `menu_tool` interprets the result

`menu_tool` (`src/agent/tools/service.py`) inspects the structured result instead of discarding it:

- All requested labels matched → return `Selected 'X' in element at label N`.
- Some or none matched → raise an exception: `Could not find option(s) [...] in dropdown at label N. Available options: [...]`. Raising is what surfaces the failure to the agent loop as a failed action rather than a silent success.
- `not_select` → raise: `Element at label N is a <tag>, not a <select> dropdown — use click_tool to open custom dropdowns.`
- `not_found` → raise: `Could not resolve the dropdown element at label N.`

### 4. Consistency: `select_option_at`

`Page.select_option_at` (`src/agent/browser/page.py`), the coordinate-based variant, gets the same JS body (element located via `elementFromPoint` + `SELECT` ancestor walk instead of xpath) so the two paths do not drift. It is currently unused by any tool but is exported on `Browser`.

### 5. Testing

New `tests/test_menu_tool.py`, following the repo's existing mock-based unit style (no live browser):

1. `menu_tool` is present in `BUILTIN_TOOLS`.
2. `menu_tool` with a mocked session returning a full-match result → success message.
3. Mocked partial/no-match result → raises, and the error message includes the available options.
4. Mocked `not_select` result → raises with the guidance to use `click_tool`.
5. Quoting: the script string generated by `select_option` for a label containing an apostrophe (`Mechanic's Lien`) embeds the `json.dumps`-encoded form (captured via a mocked `execute_script`).

## Error handling summary

Every failure mode that was previously silent now surfaces as a failed tool call with actionable text — element missing, wrong element kind, and label mismatch — which is what the agent loop needs to self-correct.

## Out of scope

- Custom (non-native) dropdown widgets.
- Fuzzy/case-insensitive label matching.
- CDP trusted-event selection (focus + keyboard simulation).
